# Data race и race condition

## Краткий ответ

| Понятие | Что это | Ловится Rust? |
|---|---|---|
| **Data race** | Два потока обращаются к одной памяти без синхронизации, хотя бы один пишет | ❌ **Нет** в safe Rust |
| **Race condition** | Логическая гонка: результат зависит от порядка событий | ✅ **Может быть** в safe Rust |

**Ключевое:** Rust **гарантирует отсутствие data race** в safe-коде, но **не защищает** от race condition — это логическая проблема.

## Что такое Data Race

**Data race** — конкретная низкоуровневая ситуация:

1. Два или более потока обращаются к **одной и той же памяти**.
2. Хотя бы **один** из них **пишет**.
3. Нет **синхронизации** между доступами.

**Результат:** неопределённое поведение (UB) — может быть что угодно: порча данных, паника, «неправильный» результат.

### Пример на C (data race)

```c
int counter = 0;

void* thread1(void* arg) {
    counter++;   // читает, изменяет, пишет — без синхронизации
    return NULL;
}

void* thread2(void* arg) {
    counter++;   // то же самое
    return NULL;
}
```

`counter++` — **не атомарная** операция. Два потока могут:

- оба прочитать `0`;
- оба записать `1`;
- итог — `1` вместо `2`.

Это **data race**. В C — UB.

### Как Rust предотвращает data race

Rust **не даёт** написать такой код **без `unsafe`**:

```rust
// ❌ Не скомпилируется
static mut COUNTER: i32 = 0;

fn main() {
    let h1 = thread::spawn(|| {
        unsafe { COUNTER += 1; }   // требует unsafe
    });
    let h2 = thread::spawn(|| {
        unsafe { COUNTER += 1; }   // требует unsafe
    });
}
```

`static mut` **не `Sync`** — компилятор **запрещает** доступ из нескольких потоков без `unsafe`. Даже с `unsafe` — это **ваша ответственность**, и **data race возможен**.

### Как Rust заставляет использовать синхронизацию

```rust
use std::sync::{Arc, Mutex};

let counter = Arc::new(Mutex::new(0));

let h1 = thread::spawn({
    let counter = counter.clone();
    move || {
        let mut g = counter.lock().unwrap();
        *g += 1;   // ✅ безопасно: мьютекс сериализует доступ
    }
});
```

- `Mutex` **сериализует** доступ.
- `Arc` даёт **разделяемое владение**.
- Компилятор **требует** этого — иначе не скомпилируется.

## Что такое Race Condition

**Race condition** — **более широкое** понятие: **логическая гонка** по времени. Результат программы **зависит от порядка** выполнения операций, который **не детерминирован**.

### Ключевое отличие

- **Data race** — про **память** (одна ячейка, без синхронизации).
- **Race condition** — про **логику** (порядок событий).

Race condition **может быть** даже **с синхронизацией** — если синхронизация **не покрывает** всю логическую операцию.

### Пример race condition на Rust

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let m = Arc::new(Mutex::new(false));
    let m2 = m.clone();

    let h = thread::spawn(move || {
        let mut g = m2.lock().unwrap();

        // ✅ Нет data race — мьютекс защищает
        // ❌ Но есть логическая проблема: check-then-act
        if !*g {
            *g = !*g;
        }
    });

    h.join().unwrap();
    println!("{}", *m.lock().unwrap());   // true
}
```

**Что здесь происходит:**

- **Data race нет** — `Mutex` защищает `bool`.
- **Race condition тоже нет** — только один поток.
- Но если добавить **второй поток**, может возникнуть **логическая гонка**:

```rust
// Поток 1: читает g = false
// Поток 2: читает g = false
// Поток 1: пишет g = true
// Поток 2: пишет g = true
// Итог: g = true — но дважды "переключили", хотя хотели один раз
```

Это **race condition** — «проверили-изменили» (check-then-act) без **атомарности** всей операции.

## Классические примеры race condition

### 1. Check-then-act

```rust
if !map.contains_key(&key) {   // проверили
    map.insert(key, value);     // изменили
}
```

Между проверкой и вставкой другой поток может **вставить** ключ. Итог — **двойная вставка** или **перезапись**.

**Решение:** атомарные операции (`entry().or_insert()`, `compare_exchange`).

### 2. Read-modify-write

```rust
let v = counter.load();
counter.store(v + 1);
```

Между `load` и `store` другой поток может **изменить** `counter`. Итог — **потерянное обновление**.

**Решение:** `fetch_add` (атомарно).

### 3. Порядок инициализации

```rust
if !initialized {
    initialize();   // между проверкой и инициализацией — гонка
}
```

**Решение:** `OnceLock`, `LazyLock`, `OnceCell`.

### 4. TOCTOU (Time-of-Check to Time-of-Use)

```rust
if path.exists() {   // проверили
    fs::read(path)    // файл могли удалить между проверкой и чтением
}
```

**Решение:** обрабатывать ошибку чтения.

## Data race vs Race condition: сравнение

| Аспект | Data race | Race condition |
|---|---|---|
| Уровень | Низкий (память) | Высокий (логика) |
| Что общего | Одна память, ≥1 пишет, нет синхронизации | Порядок событий не детерминирован |
| Ловится компилятором | ✅ Rust запрещает в safe | ❌ Не ловится |
| Результат | UB (неопределённое поведение) | Неправильный результат |
| Синхронизация помогает | ✅ Да | ⚠️ Частично |
| Пример | `counter++` из двух потоков | `if !x { x = true }` |

## Ваш пример: разбор

```rust
let m = Arc::new(Mutex::new(false));
let m2 = m.clone();

let h = thread::spawn(move || {
    let mut g = m2.lock().unwrap();

    if !*g {
        *g = !*g;
    }
});

h.join().unwrap();

println!("{}", *m.lock().unwrap());   // true
```

**Data race:** ❌ **Нет** — `Mutex` защищает `bool`.

**Race condition:** ❌ **Нет** — только **один** поток. Гонка возможна только при **конкуренции**.

**Что делает `Mutex`:**

- **Не** решает data race (её и так нет — компилятор не дал бы).
- **Решает атомарность** пары «чтение-запись»:
  - `lock()` сериализует доступ;
  - `if !*g { *g = !*g }` выполняется **атомарно** относительно других потоков.

## Что было бы без `Mutex`

```rust
use std::sync::Arc;
use std::thread;

fn main() {
    let m = Arc::new(false);   // Arc<bool> — не изменяем
    // ...
}
```

`Arc<bool>` даёт **только чтение** — изменить нельзя. Компилятор **не даст** написать data race.

Чтобы изменить — нужен `Mutex`, `RwLock`, `AtomicBool` или `unsafe`.

## Что было бы с `AtomicBool`

```rust
use std::sync::atomic::{AtomicBool, Ordering};
use std::sync::Arc;
use std::thread;

fn main() {
    let m = Arc::new(AtomicBool::new(false));
    let m2 = m.clone();

    let h = thread::spawn(move || {
        // ✅ Атомарная операция: check-and-set
        m2.compare_exchange(false, true, Ordering::SeqCst, Ordering::SeqCst).ok();
    });

    h.join().unwrap();
    println!("{}", m.load(Ordering::SeqCst));   // true
}
```

- `compare_exchange(false, true, ...)` — **атомарно**: если `m == false`, установить `true`.
- **Нет race condition** — операция **неделима**.
- **Нет data race** — атомик.

## Сводная таблица

| Аспект | Data race | Race condition |
|---|---|---|
| **Определение** | Одна память, ≥1 пишет, нет синхронизации | Порядок событий не детерминирован |
| **Уровень** | Низкий (память) | Высокий (логика) |
| **Rust safe** | ✅ Запрещена | ⚠️ Возможна |
| **Результат** | UB | Неправильный результат |
| **Ловится** | Компилятором (safe) | Тестами, ревью, анализом |
| **Пример** | `counter++` × 2 потока | `if !x { x = true }` |
| **Решение** | `Mutex`, `RwLock`, `Atomic*` | Атомарные операции, правильный порядок |
| **Ваш пример** | ❌ Нет | ❌ Нет (один поток) |
| **`Mutex` решает** | Data race (и так нет) | Атомарность check-then-act |

## Итог

- **Data race** — низкоуровневая гонка за **память**. Rust **запрещает** её в safe-коде через `Send`/`Sync`.
- **Race condition** — высокоуровневая **логическая** гонка. Rust **не защищает** от неё.
- **`Mutex`** в вашем примере решает **не data race** (её и так нет), а **атомарность** пары «чтение-запись».
- **Check-then-act** — классический race condition, который **может быть** даже с `Mutex`, если **не покрыть** всю логику.
- **`AtomicBool::compare_exchange`** — атомарная операция, решает и data race, и race condition.
- **Правило:** `Mutex` защищает **данные**, но **не логику**. Продумывайте **атомарность операций**, а не только **доступ к памяти**.
